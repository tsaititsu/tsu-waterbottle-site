# UI 與品牌規範

## 1. 基本原則

- 優先維持現有品牌與設計系統。
- 不因小修改重新設計整頁。
- 不自行更換主要字體、顏色、圓角、陰影或間距。
- 不加入與現有風格不一致的廉價模板感元件。
- 相同功能使用一致的按鈕、表單、卡片與提示方式。

## 2. 資訊層級

每個頁面要明確區分：

1. 頁面主標題
2. 主要操作
3. 重要資訊
4. 次要說明
5. 輔助內容

不可讓所有文字與按鈕都同樣醒目。

## 3. 手機版

- 以手機畫面優先檢查。
- 不得出現水平捲動。
- 主要操作按鈕要容易點擊。
- 不可讓重要功能只存在桌面版。
- 大型表格要改為可捲動、卡片或精簡欄位。
- 彈窗不得超出手機螢幕。
- 底部固定操作不可遮住內容。

## 4. 表單

- 每個輸入欄位都要有清楚 Label。
- 必填欄位要有明確標示。
- 錯誤訊息放在對應欄位附近。
- 送出中要鎖定按鈕，避免重複送出。
- 成功與失敗都要有明確回饋。
- 不可在使用者輸入完成前無故清空內容。

## 5. 狀態

所有非同步畫面要設計：

- Loading
- Empty
- Error
- Success
- Disabled
- 權限不足

不可只有正常成功狀態。

## 6. 無障礙

- 圖片使用適當 alt。
- 純裝飾圖片使用空 alt。
- 表單使用 Label。
- 按鈕名稱要說明動作。
- 鍵盤可操作主要流程。
- Focus 狀態不可完全移除。
- 文字與背景要有足夠對比。
- 不可只用紅色或綠色表達結果。

## 7. 驗收尺寸

至少檢查：

- 手機：約 390px 寬
- 平板：約 768px 寬
- 桌面：約 1440px 寬

若專案已有指定 Breakpoints，以專案設定為準。

## 8. 安心模式視覺驗收

只要修改會影響使用者看到的畫面或操作方式，Codex 必須提供白話驗收資料，不要求使用者閱讀程式碼。

至少包含：

- Preview 網址；無法取得時明確標示「尚未完成 Preview 驗收」。
- 修改前後的白話差異。
- 手機版與桌面版截圖或實際驗收結果。
- 要開啟哪一頁、按哪個按鈕、輸入什麼。
- 預期看到的正確畫面與結果。
- Loading、Empty、Error、Success 與 Disabled 是否確認。
- Console 是否有新增錯誤、相關 API 是否出現 500。

UI 修改的交付格式：

```text
請開啟：
請操作：
預期看到：
手機版：已確認／未確認
桌面版：已確認／未確認
Console／API：正常／異常／未確認
已知限制：
```

一般 UI 修改在使用者確認 Preview 後，且符合 `docs/TEST_RELEASE_RULES.md` 的其他低風險條件，才可交由 GitHub auto-merge。涉及登入、權限、付款、點數、個資或資料庫的 UI，即使只是畫面變更，仍視為高風險，不得 auto-merge。
