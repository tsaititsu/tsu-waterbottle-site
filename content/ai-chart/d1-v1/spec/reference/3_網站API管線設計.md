# SOP 重構版 v1.0｜網站 API 管線設計規格

> 用途：交給 Codex 實作。場景：客人在網頁輸入命盤 → 後端跑五步管線 → 客人拿到解讀。
> 模型：GPT-5.5（主要步驟與評審同款即可）。
> 前提：知識庫_v1.0 四檔＋SOP重構版三檔放進專案（例如 `content/sop/` 目錄），當純文字素材由程式讀取，不使用檔案上傳、不使用 RAG。

## 一、總流程

```
客人送出命盤
→ [程式] 資料核對（不用 AI）：12宮/宮干/星曜/生年四化 對照合法清單，缺漏直接擋下
→ 建立 reading job（status: running, step: 1）
→ Call 1  第一步底稿
→ [程式] 檢核1 → 不過自動重跑（最多2次）
→ Call 2  第二步
→ Call 3  第三步
→ Call 4a–4d  第四步 7A（12來源宮拆4批，每批3宮12條；四批可「並行」呼叫）
→ Call 4e  7B＋4A＋4B（輸入為48條7A）
→ Call 5  第五步客戶版
→ [程式] 檢核5（字數/標記/禁用詞/引用量）→ 不過帶原因重跑（最多2次）
→ Call 6  評審（獨立呼叫，只評不寫，輸出判定JSON）
→ 通過：存檔、顯示給客人
→ 不通過：把評審證據餵回 Call 5 重寫一次；仍不過 → 標記「待老師確認」不自動交付
```

呼叫總數：9–10 次。4a–4d 並行的話，總時長約等於 6 次串行呼叫。

## 一之二、命盤輸入標準格式（網頁表單 → 後端統一轉這個文字模板）

```
命主：＿＿（稱呼）｜性別：＿｜生年天干：＿（用於核對生年四化）
身宮：在＿＿宮
命盤：
命宮｜地支＿｜宮干＿｜主星：＿＿｜輔星：＿＿｜煞星：＿＿｜生年四化：＿＿
父母宮｜…（12 宮同格式，無星寫「空宮」）
```

程式送 AI 前先驗證：12 宮齊全、地支宮干合法、星曜名在知識庫清單內、生年四化與生年天干對照知識庫 A 四化表一致、身宮必填。任何一項不符直接擋下回報，不進管線。

## 二、每次呼叫的組裝

system prompt（固定字串放最前面，吃 prompt caching 省錢）：

```
[0_主控.md 全文]
[該步任務卡全文]（Call 5 另加 2_風格與品管.md 的「風格層」段）
[知識庫注入段]（見下表）
```

user message：

```
[命盤原始資料]
[前置步驟產出]（見下表）
執行任務卡 N。
```

| 呼叫 | 知識庫注入 | 前置產出輸入 | 建議輸出上限 |
|---|---|---|---|
| 1 | A 全文＋C 全文＋B1/B2 命中條目 | — | 16k tokens |
| 2 | A 的四化節 | 第一步全文 | 8k |
| 3 | 無（沿用第一步語意） | 第一、二步全文 | 8k |
| 4a–4d | A 的四化表 | 第一～三步全文＋該批 3 個來源宮指定 | 各 16k |
| 4e | 無 | 48 條 7A 全文 | 8k |
| 5 | 無 | 第一～三步＋7A（可只給每條的三句翻譯＋白話收束）＋7B＋4A/4B | 16k |
| 6 | 2_風格與品管.md 品管節 | 第五步正文（僅標記之間） | 2k |

B1/B2 命中條目的找法（純程式）：掃描命盤 12 宮，凡「兩顆十四主星同宮」或「單主星且對宮為指定組合」，用組合名＋地支對 B1/B2 的 `###` 標題做字串比對，抽出該條目全文注入。

參數建議：步驟 1–5 temperature 0.7、top_p 1；評審 temperature 0。全部設 `reasoning_effort`／思考預算為中即可（第四步可調高）。

## 三、程式檢核（第一級品管，不花 AI）

```ts
// 檢核1：12 宮標題齊、每宮至少一顆星、每格有分面行
// 檢核4：7A 條數 === 48，每條含十欄標題，且「生活翻譯三句」非空
// 檢核5：
//   - 有【正式客戶版開始】【正式客戶版結束】且中間 2500–4000 字（中文字元計）
//   - 禁用詞掃描（清單在 2_風格與品管.md），命中回傳原句陣列
//   - 引用量：不可對「正文」做宮位名計數——會逼模型在客戶版堆名詞，跟風格層衝突。
//     改成兩道：程式檢查「全素材整合表」10 類是否全部有填；正文涵蓋度交給評審呼叫判斷。
//   - 「你不是」出現次數 / 段落數 < 0.4
```

檢核不過的重跑訊息固定格式：

```
上一版未通過程式檢核，原因：{原因碼}，違規原句：{列表}。
請依同一張任務卡重寫，只修正違規處，其他內容保持。
```

## 四、評審呼叫（第二級品管）

system＝2_風格與品管.md 的品管節＋❌→✅ 對照表。user＝第五步正文。要求輸出：

```json
{ "判定": "通過|待修", "評分": {"命理方向":1-5,"生活畫面":1-5,"客戶可讀":1-5},
  "原因碼": [], "證據": [], "修正方向": [] }
```

任一評分 ≤3 即「待修」。用 JSON mode／structured output 保證格式。

## 五、背景執行與前端（Vercel 環境）

- 單一 HTTP request 跑不完 9 次呼叫，必須做成背景 job：
  - 簡單做法：`readings` 表加 `pipeline_status`（step1_running / step1_done / … / judging / done / needs_teacher），每步一個背景函式接力，或用 Inngest/QStash 這類 queue。
  - 前端輪詢 status，顯示進度：「正在推導 12 宮底稿（1/6）…」。全程估 2–5 分鐘，提示客人可稍後回來看。
- Supabase 每份 reading 存：命盤原始資料、各步全文、判定 JSON、耗時與 token 用量。
- 顯示給客人：只有第五步正文（可加 7B 事件稿當「重點事件」區塊）。第一～四步底稿與判定是老師後台才看得到。

## 六、老師後台（品質飛輪）

1. 後台列表：每份 reading 的判定 JSON＋正文，老師可標「金標」或直接修句。
2. 老師修過的句子累積成對照樣本，之後只回饋到兩個地方：知識庫條目、任務卡範例。不新增規則。
3. 金標命盤 2–3 張入庫；每次改 prompt 或知識庫，用金標重跑比對再上線。

## 七、產品分級（選配）

| 版本 | 管線 | 交付 | 適用 |
|---|---|---|---|
| 完整版 | 全五步 | 2500–4000 字完整交付稿＋重點事件 | 正式付費解盤 |
| 快速版 | 第一步＋第二步＋第五步（1500–2499 字主軸摘要） | 長版主軸摘要 | 低價體驗、引流 |

快速版保留第二步：生年四化是個性主軸的核心來源，不可省；省的是第三步對宮對接與第四步飛化。第五步任務卡規則不變，僅字數區間下修、整合表縮為 6 類（本質／人際／家庭／感情／工作金錢／提醒）。

## 八、給 Codex 的實作順序

1. 建 `content/sop/` 放 7 個 md 檔；寫 loader 與 B1/B2 條目比對函式
2. 寫 `runStep(n, chartData, priorOutputs)`：組 prompt → 呼叫 → 回傳全文
3. 寫三個程式檢核函式＋重跑包裝
4. 串 job 狀態機（Supabase status 欄位＋接力觸發）
5. 寫評審呼叫＋判定入庫
6. 前端進度頁＋結果頁（只渲染第五步正文與 7B）
7. 老師後台（列表、全文、判定、金標標記）
